# 历法 / 纪年系统设计（基础层）

> 状态：🧪 讨论中 · 2026-08-24
> 目的：灵框时间线的日期存储，从「硬编码 360 天/年的小数年份」升级为「可自定义的纪年系统」。
> 范围：**只定基础层数据模型**。多纪元自动切换、跨历法换算、循环层冲突处理等复杂决策**留给管理层 AI**（见§8）。

---

## 1. 为什么必须改（现状痛点）

当前 `TimelineNode.year: number` 是**内部小数年份**，`SEC_PER_YEAR = 31104000`（=360天×24×3600）全局写死，`parseTimeText()` 把年月日时分秒全部折算进一个小数 year。

- **精度丢**：`Math.round(y*1e6)/1e6` 只保留到 1e-6 年 ≈ 31 秒 —— 秒级输入在反推时已坏。
- **历法写死**：360 天 / 30 天月一年，无法表达「白石历」「第三纪元 42 年」这类自定义历法（ROADMAP §3 已列入需求）。
- **信息压平**：用户输入的结构化年月日被压成一个小数 + precision，反推是二次近似，月末/负数年有偏差。
- **绝对年与分层纪元对不上**：只有一条绝对时间轴（负=公元前），没有「某纪年法起点 + 计数」这个显示层。

## 2. 核心抽象：两种纪年，一个模型

用户切分（2026-08-24）：

| 类型 | 例子 | 特性 |
|---|---|---|
| **进制纪年** | 公历 秒→分→时→日→月→年 | **进位**，满 X 进一层，决定位置，能换算成绝对刻度 |
| **平行纪年** | 天干(10)/地支(12)/生肖(12)/轮回圈 | **不进位**，各环独立循环，只做标签，不决定排序 |

二者统一为同一个结构：**一个时间点 = 一串有序的「层」**，从最顶层往下。

**层的权威定义（B 模型，2026-08-24 拍板）**：一个层 = 一个数组，每个元素 = 该位置把上一层拆成几份。

```
一个层 = { id: string, values: number[] }
  values.length  = 这个层向上拆几份（该层有几个位置）
  values[k]      = 第 k 个位置再往下拆几份（下标从 1 开始）
```

- **固定层 = 单元素数组**（用户洞察）：`year:[12]`（全年拆12月）、`day:[24]`（一天24时）、`hour:[60]`、`minute:[60]` —— 单元素表示"全层统一，不随位置变化"
- **可变层 = 多元素数组**：`month:[31,28,31,30,...]`（大小月）、闰年版 `[31,29,...]` —— 才是真正要用户填的

**并列开放**：一个层既可以是"序列"（手填数组），也可以是"函数"（预设计算，如格里高利闰年、干支）。统一通过 `width(layer, idx, ctx)` 接口访问，上层不区分是查表还是计算。

**两层分工**：
- **单位层**（物理进制，内建，一般不改）：day=24、hour=60、minute=60 —— 单元素数组
- **历法层**（文化/故事设定，用户配置）：年拆几月、月长、纪元、干支、轮回圈

**最顶层永远是 anchor**：无限制整数（年）或具名（年号），它没有上级，不参与进位。

关键结论：**平行环本质是从 anchor 折算出来的**（干支 = 年 mod 周期 + 相位），它不是独立事实源，是 anchor 的一张循环映射表。

## 3. 权威事实源的三角关系

上一版「存完整序列」在**整齐进制历**下成立（序列↔刻度能干净互推），但遇到**闰年/大小月**就露馅：

- 序列 `[2024, 2, 29]` 里，「今年是闰年」这个事实不在序列里，2023 也有 2 月但没有 29 号。
- 只存序列 + 不存历法规则 → 还原不出来；存序列 + 存历法规则 → 序列冗余（刻度 + 历法能无损还原序列）。

所以**「完整序列」不能当唯一事实源**，正确关系是：

```
权威事实源  =  单调整数刻度（绝对基准单位）   ← 排序/循环/时间指针全部走它
        ↑            历法定义做双向换算            ↓
人类可读层  =  完整序列（[年,月,日,时,分,秒] + 可选年号）  ← 显示/输入
```

- **存**：整数刻度 + 历法定义（刻度为权威，历法为翻译官）
- **还原**：刻度 + 历法定义 → 无损还原序列（序列不必双份落盘，除非要保留用户原始输入做审计）

## 4. 类型定义

### 4.1 层（历法 / 单位）

```ts
/** 一个层 = 一个数组，每个元素 = 该位置把上一层拆成几份（B 模型） */
interface Layer {
  id: string;            // 'year'|'month'|'day'|'hour'|'minute'|'second' | 自定义
  values: number[];      // 单元素=固定层；多元素=可变层（大小月）。下标从 1 开始
  variants?: Record<string, number[]>;   // 如 { normal:[31,28,...], leap:[31,29,...] }（闰年切换）
}

/** 历法定义：mode 决定换算主路径 */
interface Calendar {
  id: string;
  name: string;                    // '白石历' | '公历'
  mode: 'function' | 'table';      // 换算主路径：函数（默认，快）/ 列表（降级，慢）
  fn?: string;                     // function 模式下的内建预设 id：'gregorian'|'fixed360'|...
  anchor: { year: number } & { epochs?: Epoch[] };
  layers: Layer[];                 // 分层定义（table 模式用）：month/day/hour/minute
  unit: UnitSystem;                // 单位层（物理进制，内建）：day=24/hour=60/min=60
  switches: LayerSwitch[];         // 闰年/干支等切换（table 模式用）
}

/** 单位层：物理进制（内建），与历法层（文化设定）分开 */
interface UnitSystem {
  day: number;      // 一天几小时（默认 24）
  hour: number;     // 一小时几分（默认 60）
  minute: number;   // 一分几秒（默认 60）
}

/** 切换规则：周期性 cycle，决定某层用哪个变体（闰年/干支与同构） */
interface LayerSwitch {
  id: string;
  period: number;              // 周期：4（闰年）/ 60（干支）
  map: Record<number, string>; // 当前值 mod period → 变体 id
  source?: string; offset?: number;
}
```

**函数主路径 + 列表降级（2026-08-24 拍板）**：
- `mode='function'`（默认）：换算走内置函数预设（`fn` 指定），O(1) 计算、性能好
- `mode='table'`：换算走手填列表（`layers`/`variants`），能表达极复杂历法但**显著降性能**，是设置里的可选项

- **白石历（360/30）**：`mode:'function', fn:'fixed360'` → 纯净，零表
- **公历（365/366）**：`mode:'function', fn:'gregorian'`（闰年函数内建）；或 `mode:'table'` 用 `variants.normal/leap` 手填
- **天干地支**：`switch` 周期 60 折算，与闰年同构

### 4.2 时间点（完整序列）

```ts
/** 一个时间点 = 完整序列 */
interface TimePoint {
  anchor: { epochId?: string; year: number };  // 顶层：无限制整数 + 可选年号
  values: Record<string, number>;              // 各层值：{month:7, day:15, hour:9, ...}
}
```

人类可读形如：`白石历 300 年 · 7 月 15 日 · 9 时 30 分 · 又逢「乙巳」`（干支 = cycle 从 anchor 派生）。

## 5. 换算（唯一的关键函数）

```ts
// 1) 先确定当前处于哪个模式（由切换规则决定）
modeId = pickMode(switches, anchor.year)    // 年 mod 4 → 'leap' / 'normal'；干支同理

// 2) 进制层 → 整数刻度：按该模式的样式表逐层累加，无浮点
epoch = anchor.year * yearUnit
      + Σ over 层: 位置值 * 该层样式查表得到的 unit     // 月长从模式 styles 查

// 3) 循环层 → 标签（= 模式切换的逆方向，不进位、不参与 epoch）
cycleVal = (anchor.year + phase) mod period            // 干支 = year mod 60 再拆 十/十二
```

- 这是旧 `SEC_PER_YEAR` 的**推广版**：360 天制 = 一种模式、月样式全 `[30,...]` → 每层 unit 固定，退化为纯线性
- 公历 365/366 = 平/闰两模式，月样式查表决定每层实际 unit（2月 28 或 29）
- **整数刻度 + 整除 → 秒级无损**，旧小数年 31 秒舍入坑直接消失
- **关键**：样式/模式只决定"怎么把年月日换算成刻度、怎么显示"，藏在历法定义内部，**不污染外部排序/循环/时间指针**

## 6. 对现有代码的影响（关键：尽量零破坏）

- `timeline.ts` 里 `xToTime`/`timeToX`/循环 span/gap/时间指针，需要的只是一个单调数 —— 换成 `toEpoch(timePoint)` 的整数刻度即可，逻辑照用。
- 360 天制种子数据：`origin=0, unit=86400...` 直接映射，现有数据兼容。
- **刻度单位**：见 §7 待确认，倾向「整数年+天数」这种历法原生刻度（更配虚构世界观），秒只在需要时刻的场景露出。

## 7. 开放问题（待用户拍板）

### 7.1 样式 / 模式 / 切换（最终模型，2026-08-24 用户拍板）

用户明确：**不做生成器/间隔压缩推断**，历法就是「用户手填的序列 + 模式」。

| 概念 | 定义 | 例子 |
|---|---|---|
| **样式（style）** | 某层的一串完整值序列，**用户手动填** | 月长 = `[31,28,31,30,31,30,31,31,30,31,30]` |
| **模式（mode）** | 一套样式的组合（一个历法变体） | 平年模式 / 闰年模式 |
| **切换规则** | 一个周期性的 cycle，决定用哪个模式 | `year mod 4 == 0` → 闰年，否则平年 |

- **整齐历（白石历 360/30）**：一种模式、一种样式 `[30,30,30,...]`，零切换规则 → 极简
- **公历（365/366）**：平年/闰年两模式，各一张月长样式表，切换 = `year mod 4`（+400 例外）
- **天干地支**：也是"模式切换"，与 cycle 层完全同构

**没有"智能推断/自动生成"，全是用户手填的样式 + 周期切换。** 这正是用户最初说的"储存完整序列"——存的就是手填序列，不做二次推断。

## 8. 留白给管理层 AI（基础层不做）

1. **多纪元自动切换 / 推理**：一个历法多个年号、某年号对应绝对哪年的对齐推导
2. **跨历法换算**：两个 Worldset 不同历法怎么互算（旧 `absOffset` 的升级版）
3. **循环层冲突处理**：干支与 anchor 年对不上时听谁的 —— 基础层只做「anchor 派生 cycle」这一条默认路径
4. **历法编辑器 UI（含间隔选取 / 批量设置）**：选样式作用层 → 设循环间隔 → 批量给一串值（用户 2026-08-24 明确"到时候再搞"）—— 基础层只提供"样式表能被这样编辑"的数据结构（`Style.values` 可整体读/写），UI 实现留给管理层 AI
5. **复杂不规则历**：闰月、真公历闰年、2 月 28 天 —— 已并入样式/模式模型（`Mode.styles` 手填序列 + `ModeSwitch` 切换），默认先按 360/30 跑通
6. **多层层级历法（可选需求，2026-08-24 用户提出："不确定层有三四层"）**：现有换算 `toEpoch`/`fromEpoch` **硬编码年→月→日→时→分单链**，只支持三层以内。若遇 `年 → 季/旬/候 → 月 → 日` 或多层嵌套历法，需**把换算泛化为按 `layers` 数组逐层递归累加**（不做层名假设）。⚠️ 暂不实现，作为可选需求记录——等确认有真实三/四层历法场景再泛化，避免过度设计
6. **用户自定义规则算法（2026-08-24 用户定案）**：**不做图形化编程**（那是复杂度黑洞）。正解 = **让灵框内置 AI 助手直接写函数**——真到非常复杂的历法（如"每3年闰、闰年13个月"），用户求助手生成一个历法函数，注册为新的 `fn` 预设，走 `mode:'function'`（O(1)，跟内建预设同级，不降性能）。用户视角 = 跟选"格里高利"一样选"我的历法"。
   - **复用**：走同一套 `width()/daysInMonth/daysInYear` 分派接口
   - **关键：AI 生成函数要做好规范要求**，建议 5 条：
     1. **纯函数、无副作用**：`daysInMonth(year,month)` / `daysInYear(year)` 可重复、不依赖外部状态
     2. **确定性**：同一输入永远同一输出（历法规则必须确定，不能随机/依赖时间）
     3. **边界约束**：月 1~12、天合法区间，不返回 NaN/负数
     4. **签名固定**：必须实现 `fnDaysInMonth` / `daysInYear` 接口（即基础层的分派入口，已建好）
     5. **可验证**：AI 生成后跑一遍自检（`toEpoch/fromEpoch` 互逆 + 闰年边界）通过才注册——防 AI 产出 bug
   - 留给管理层 AI；`Calendar.fn` 已留成可扩展注册表
